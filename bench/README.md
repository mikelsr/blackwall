# Blackwall vs Anubis benchmark

> [!WARNING]
> **`bench/` was generated by AI** (Claude), under the direction of Blackwall's author: the load generator, the scripts, the experiments and these documents. Read it with that in mind.

This directory compares Blackwall with [Anubis](https://github.com/TecharoHQ/anubis) on equal terms: the same backend, rules, cryptography, CPU budget and load, with logging off and in-memory stores on both. It measures how many requests each serves before slowing down, the CPU each request costs, latency and memory, and then explains the differences with profiles and targeted experiments.

- **Results:** [`REPORT.md`](REPORT.md) has the method, how the numbers were checked, and what came out. The article ["Benchmarking Blackwall Against Anubis"](https://mikelsr.github.io/posts/benchmarking-blackwall-against-anubis/) tells the same story for readers.
- **Running it:** [`RUNNING.md`](RUNNING.md), on a Mac or on a Linux box over SSH, with every setting and how to read the output.

## Quick start

```sh
git submodule update --init   # Anubis's source, at the tested commit
bench/build.sh                # bin/blackwall, bin/anubis, bin/loadgen, bin/backend
bench/run.sh                  # capacity of both servers, every scenario: hours
MODE=fixed FIXED_RATE=2000 bench/run.sh   # CPU per request at the same load
```

Results go to `bench/results/<timestamp>-<mode>/`, with `summary.md` for people and `results.jsonl` for tools. Use Linux for numbers you publish: `run.sh` pins each process to its own cores there, and macOS can't.

## What's here

| path | what it is |
|---|---|
| [`REPORT.md`](REPORT.md) | method, validation and results |
| [`RUNNING.md`](RUNNING.md) | how to run it, settings, reading results, troubleshooting |
| `anubis/` | Anubis's source, a **git submodule** pinned to the commit tested (207f9eb8, 1.28.1 plus ten commits). `git submodule update --init` checks it out; `build.sh` builds it unpatched |
| `build.sh` | builds everything into `bin/` |
| `run.sh` | runs the benchmark: for each policy, scenario and server, a freshly started server under load from `loadgen` |
| `remote.sh` | the same on a remote box over SSH: sync the tree, build, run in `tmux`, fetch the results |
| `backend/` | the website behind both proxies: answers with a body of `?size=N` bytes and counts its connections |
| `loadgen/` | the load generator: open loop (requests leave on schedule, whatever the server does), scenarios, CPU and memory sampling, summaries |
| `policies/` | the two rule sets: `minimal` (three rules) and `realistic` (each server's stock rules) |
| `profile-split.sh` | splits a CPU profile of either server into the same parts, to compare where the time goes |
| [`experiments/`](experiments/README.md) | the scripts behind each investigation in `REPORT.md` |
| `blogdata/` | builds the article's graph data (`data.json` in the blog) from raw results, so no number is copied by hand |
| `bin/`, `results/` | build output and raw results; not committed |

## Keeping it current

- **Updating Anubis:** move the submodule to the new commit, then copy its `data/` (minus Go files) over Blackwall's `data/`, so both servers evaluate the same rules with `realistic`. `cargo test` compiles every bundled rule file.
- **Regenerating the article's data:** `cd bench && go run ./blogdata -out <blog>/src/assets/graphs/articles/2026-10-21/data.json`. Which runs feed which graph is set at the top of `blogdata/main.go`.
